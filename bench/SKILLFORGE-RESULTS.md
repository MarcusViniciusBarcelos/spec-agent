# skill-forge bench — longitudinal reuse (in-environment)

> Method: inside a coding agent (Claude Code, `haiku`), isolated subagents with no tools. Tests whether a skill **generated by skill-forge** (review heuristics learned from a project's history) improves later tasks vs not having it in context. A no-tools subagent is a clean knowledge-injection test (the "without skill" condition can't "discover" the invariant by grepping the codebase).
>
> The tasks below are **anonymized**: the real skill was generated from a private project; here we describe only the *shape* of the heuristic, not the project's source.

## The question

Does durable knowledge captured in a skill pay off on reuse? Where — and where is it just shadowing (the model already knew)?

## Suite — 3 tasks × 2 conditions (without skill / with skill)

| # | task | heuristic | type |
|---|---|---|---|
| L1 | review a PR that moves an event-publish call from INSIDE the transaction to AFTER commit | framework invariant: the publish is **already** deferred to post-commit | obvious answer misleads |
| L2 | read a field of a typed DTO (generated client) that arrived snake_case in one env | convention: responses are camelCase; fix the type at the source, **don't** use a fallback | project convention |
| L3 | write `debounce(fn, ms)` | none (control) | general knowledge |

## Result

| task | without skill | with skill | differential |
|---|---|---|---|
| **L2 (casing)** | added a defensive `?? field_snake` fallback (wrong) — *cited the rule and broke it anyway* | read the field as plain camelCase, fix at the source (right) | **clean flip** ✅ |
| **L1 (publish-in-tx)** | REJECTED for the wrong reason → recommended building an outbox (unnecessary work) | REJECTED: "the framework already defers the publish, don't refactor" (right) | soft — avoided over-engineering, didn't flip the verdict |
| **L3 debounce** | correct | correct (identical) | **none** ✅ (no bias) |

## Honest reading

- **L2 is the strong, most instructive win**: the base model *knew* the rule (it even cited a prior memory of the same content) and still rationalized the "defensive" fallback. The skill, in **imperative/checklist** form ("DON'T use a fallback; fix at the source"), blocked the rationalization the verbose memory didn't. **Form of the skill > existence of the rule.** Available knowledge ≠ applied knowledge.
- **L1 shows the right kind of knowledge**: the invariant (a framework that already collects the publish and flushes it AFTER commit) is project-specific and the base model can't know it — without the skill it proposes an outbox (unnecessary engineering). But the *verdict* didn't flip (both rejected the PR), so the gain is "correct rationale / avoids busywork," not "avoids a bug."
- **L3 clean control**: an irrelevant skill → zero effect. Confirms the L1/L2 gain is from the right heuristic, not from "the skill makes the agent generically more careful."

## Conclusion

Skill reuse pays off on **project-specific knowledge the model applies wrong on its own** — especially conventions where the plausible default violates the rule (L2). It's **cheap** (the skill enters context via the agent's skill system, marginal cost) and **localized**. Unlike council (5× tokens, marginal calibration gain), skill-forge is the **cheap, durable** side of the harness. Caveat: N=1 per task; what matters is the pattern (a flip on a convention, neutral on the control), not the rate.
